Ivy’s core concept

Ivy is not “a sync script.”

Ivy is a declarative distribution engine:

“Given these sources, render these artifacts, and place them into these targets, with layered config and predictable precedence.”

That framing lets you sync anything to anywhere.

The repo you described: “configuration + assets”

Yes — Ivy should treat a repo as a Garden.

A Garden contains:

  • assets (files to distribute)

  • manifests (what to install where)

  • overlays (machine / project / OS specifics)

  • variables (path conventions, usernames, etc.)

  • optional sync backends (git, obsidian vault, cloud, etc.)

The Garden is the source of truth

Ivy’s job is to take the Garden + your current context and produce an installation plan.

The layering model you want

You said: global + per-box + per-project + other stuff.

Let’s make that crisp and powerful:

Configuration scopes

  1. global: applies everywhere

  2. profile: “role-based” (work, personal, teaching, research)

  3. platform: OS + shell + editor (mac/windows/linux)

  4. machine: hostname / device ID / “this box”

  5. project: repo-local overrides (or detected by markers)

  6. session: CLI overrides for one run

Precedence (last wins)

global < profile < platform < machine < project < session

This is the magic that makes Ivy feel effortless.

1) Bidirectional sync: the right mental model

To do this safely, Ivy needs a canonical source per artifact, otherwise you get merge hell.

So for every “thing” (AGENTS.md, rules, templates, prompts), Ivy should know:

  • Canonical path (the one true editable file)

  • Mirrors (copies/symlinks placed elsewhere)

  • Mode (copy, symlink, template render)

    • one_way: garden → targets (classic)

    • two_way: canonical ↔ mirrors, and canonical ↔ git

  • Conflict policy (last-write-wins, prompt, abort, 3-way merge)

The cleanest approach

Canonical lives in the Garden repo.
Everywhere else on the box is a mirror.

Then if you edit a mirror, Ivy can:

  1. detect the change

  2. propagate it back to canonical

  3. commit + push

  4. later pull + apply on other boxes

That gets you your dream loop with minimal ambiguity.

2) How Ivy detects changes (without being annoying)

Two modes:

Manual “pull/push” workflow (v1)

  • ivy pull → git pull --ff-only + apply to mirrors

  • ivy push → collect changes from mirrors → update canonical → commit + push

  • ivy sync → does both (push then pull then apply), configurable

This is reliable and easy to reason about.

Watch mode (v2, but very doable)

  • ivy watch (daemon-like)

    • watches mirror locations + canonical

    • on change: runs a “plan”, then applies according to policies

    • batches changes (debounce) so it doesn’t commit 800 times

On macOS you can use FSEvents, Linux inotify, Windows ReadDirectoryChangesW (Python libs exist). Cross-platform watch is very doable.

3) Automatic pulls: “before I even sit down”

Two patterns:

A) “On login / on shell start”

  • Ivy installs a tiny hook:

    • ivy auto pull at login

    • or ivy pull when opening a terminal (optional)

B) “Always-on background service”

  • ivy watch --auto-pull

    • periodically polls remote (or uses git fetch)

    • if remote advanced and clean → pull + apply

    • if local dirty → alert / pause

This gives you: push on Box A → Box B updates before you arrive.

Important safety rule: auto-pull must not clobber uncommitted local edits. So Ivy needs a “dirty working set” check and a clear policy.

4) Conflict handling: this is where tools die if sloppy

Ivy needs explicit conflict semantics, per artifact.

For example:

  • AGENTS.md: allow merge (git handles it well)

  • editor commands: canonical wins (don’t merge generated stuff)

  • machine-specific configs: machine overlay wins

When a conflict occurs, Ivy should:

  • stop and show a clean diff

  • offer choices:

    • keep local mirror

    • keep canonical

    • open merge tool

    • stash local + apply remote

  • record what happened (audit log)

🧠 The Critical Design Decisions

Before we go further, we need to cement 5 pillars.

1️⃣ Canonical Truth Model

Every artifact must declare:

  • canonical: one authoritative location (usually in Garden repo)

  • mirrors: one or more distributed locations

  • direction: one_way or two_way

  • conflict_policy

This avoids ambiguity.

Without canonical mapping, bidirectional sync becomes chaos.

2️⃣ Git as State Database

Git is not just storage.

It becomes:

  • change history

  • box-to-box propagation layer

  • optional cross-box status registry

  • rollback mechanism

That means Ivy should:

  • never auto-force-push

  • always check working tree cleanliness

  • optionally isolate its own branch (e.g., ivy-state)

3️⃣ Drift Detection Engine (Core Magic)

Every file gets:

  • content hash

  • last_applied hash

  • origin (canonical or mirror)

  • last_modified timestamp

Ivy compares:

  • canonical vs mirror

  • mirror vs last_applied

  • canonical vs last_applied

This lets Ivy detect:

  • mirror-only edits

  • canonical-only edits

  • true conflicts

  • no-op

This engine is the heart of bidirectional safety.

4️⃣ Sync Modes

You actually want three modes:

Safe Manual Mode (v1 default)

Explicit commands only:

ivy pull

Assisted Mode

On command, Ivy can:

  • auto-commit

  • auto-push

Concept model we’ll keep stable from the start

1) Gardens

A Garden is a source package containing:

  • assets

  • manifests

  • overlays

  • templates

  • status registry (optional)

You can have many:

  • work-garden

  • personal-garden

  • teaching-garden

  • lab-garden

2) Profiles

A Profile is a named selector bundle:

  • work

  • personal

  • teaching

  • phd

Profiles decide what gets installed and where.

3) Boxes

A Box is a machine identity:

  • hostname

  • OS/arch

  • optional tags: laptop, desktop, workstation, airgapped

A box can have local overrides that never leave that machine.

4) Projects

A Project is a detected context:

  • repo root

  • tags

  • per-project overlays

The config layering we’ll keep (even in v0)

Precedence (last wins):
global < garden < profile < platform < box < project < CLI

So even in v0, the shape is correct.

🌿 1. What Is Ivy Not?

This is critical.

If we don’t define her boundaries, she becomes:

  • A dotfile manager

  • A secret manager

  • A package manager

  • A deployment orchestrator

  • A config framework

  • A CI system

All of which are tempting.

We should explicitly decide:

  • Is Ivy allowed to manage .zshrc?

  • Is Ivy allowed to manage secrets?

  • Is Ivy allowed to modify arbitrary system paths?

  • Is Ivy allowed to auto-run arbitrary scripts?

If we don’t limit scope early, complexity will explode.

My instinct:

Ivy distributes declarative artifacts and manages drift.
She does not execute arbitrary code from gardens.

But we should decide.

🌿 2. Safety Model

This matters more than features.

We need to define:

  • Does Ivy ever overwrite without confirmation?

  • What happens if Git working tree is dirty?

  • What happens if canonical and mirror both changed?

  • What happens if remote changed and local changed?

We need a default stance:

Default = cautious and transparent.
Power users can opt into automation.

🌿 3. Symlink vs Copy

This is bigger than it sounds.

Options:

Copy model

  • Safe

  • Predictable
    − Drift detection required
    − Promotion logic required

Symlink model

  • No drift detection needed

  • Single source of truth
    − Breaks on Windows sometimes
    − Users edit the link target without realizing

For bidirectional workflows, symlinks simplify everything — but they reduce portability.

We should consciously decide which is default.

🌿 4. Git Strategy

We need to decide:

  • One branch per garden?

  • Separate “state branch” for box status?

  • Commit style (Ivy-generated vs user-generated)?

  • Signed commits?

  • Auto-commit messages standardized?

This affects long-term reliability.

🌿 5. Identity and Host Detection

How does Ivy know a box is “platinumplatypus”?

Hostname?
UUID?
User-configured name?

If two machines share hostname (common in VMs), what then?

We need a deterministic box identity system.

🌿 6. Performance & Scale

Today:

  • 20 artifacts

  • 3 machines

In a year:

  • 300 artifacts

  • 6 gardens

  • 8 machines

  • multiple projects

Do we:

  • hash everything every run?

  • cache state?

  • store per-artifact metadata?

  • track last-applied state file?

We should decide if Ivy maintains a local state file like:

JSON
~/.config/ivy/state.json

That affects drift detection performance and clarity.

🌿 7. Permissions and Cross-Platform Edge Cases

Real-world friction points:

  • Windows path separators

  • NTFS vs POSIX permissions

  • executable bits

  • case sensitivity differences

  • long path limits

  • symlink privileges on Windows

We don’t have to solve everything day 1 — but we need a philosophy:

Lowest common denominator?
Or platform-specific adapters?

Even if it’s minimal in v1.
